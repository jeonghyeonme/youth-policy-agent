# 공공 API 사전 조사

후보 공공 API 다섯 개의 명세와 실제 응답을 조사한다. 목표는 세 가지 판단에 쓸 자료를 만드는 것이다. 어떤 API를 묶을지(Q1), 서술형 자격조건을 누가 판단할지(Q4), 의미 검색이 필요한지(Q8).
[D1](../../docs/decisions/D1.md)에 따라 데이터는 미리 수집해 JSON 파일로 두므로, 이 조사의 수집 스크립트가 나중에 서비스의 수집기가 된다.

지금까지 확인한 명세는 [findings.md](findings.md)에, 키 발급 절차는 [api-keys.md](api-keys.md)에, 공통 정책 형식 초안(W3)은 [schema.md](schema.md)에 있다.

각 단계는 확인할 수 있는 산출물로 끝난다. 앞 단계가 확인되기 전에는 다음 단계로 가지 않는다.

## 샘플 수집 실행 (W2)

저장소 루트에서 실행한다. 키가 비어 있는 출처는 건너뛴다. 이미 받은 파일은 다시 호출하지 않으므로, 중간에 실패해도 다시 실행하면 된다.

```bash
python3 experiments/api-survey/collect_samples.py   # Windows: py experiments/api-survey/collect_samples.py
```

결과는 `samples/<출처>/<기능>-<페이지 또는 ID>.json`에 저장된다. 파일마다 원본 응답(`body`), 요청값(키 제외), HTTP 상태, 받은 시각이 들어 있다. 공개 데이터이고 키가 없으므로 커밋해서 팀과 공유한다.

| 출처 | 첫 실행 호출 수 | 받는 것 |
| --- | --- | --- |
| 잡알리오 | 7 | 진행 중 공고 목록 2페이지(최대 200건), 상세 5건 |
| LH | 최대 8 | 최근 60일 공고 목록 최대 3페이지, 임대 공고 상세 5건 |
| 복지로 중앙부처 | 21 | 목록 1회(최대 500건, 전체), 상세 20건(생애주기에 청년이 있는 서비스 우선) |
| 복지로 지자체 | 12 | 목록 2페이지(200건), 상세 10건(청년 우선) |
| 온통청년 | 약 40 | 전체 목록(100건씩) |

## 단계별 내용

**W1 명세 카드.** data.go.kr 페이지에 들어 있는 Swagger를 읽어 API별 카드를 만든다. 카드에는 엔드포인트, 요청값, 응답 필드, 페이지당 최대 건수, 한도, 호출 패턴을 담는다. Swagger가 없는 LH와 로그인이 필요한 온통청년 필드표는 손으로 채우고, 손으로 채운 칸을 카드에 표시한다.

**W2 샘플 수집.** 키는 환경변수(`YOUTHCENTER_API_KEY`, `DATA_GO_KR_SERVICE_KEY`)로만 읽는다. API별 호출 예산은 아래와 같다.
- 온통청년: 전부(3,981건).
- 잡알리오, 복지로 지자체: 대표 조건별 목록 몇 페이지, 상세 몇 건.
- LH: 최근 공고 목록. 상세 API는 활용신청이 되면 몇 건.
- 복지로 중앙부처: 목록 1회(`numOfRows=500`)와 상세 20건 이내. 목록에서 청년 대상 건수를 세어 전체 수집 기간을 다시 계산한다.

**W3 공통 정책 형식.** 자격조건을 세 칸으로 나눈다. 서버가 거르는 **코드 조건**(나이, 지역, 소득 구분, 학력, 취업상태), LLM이나 사용자가 판단하는 **서술형 조건**, 응답에 없고 **첨부파일에만 있는 조건**이다. 이 형식은 다른 사람 코드가 기대는 형식이므로 확정은 PM이 한다.

**W4 응답 분석.**
- 필드별 채움률. 빈 값과 "제한없음" 비율을 센다.
- 코드로 거를 수 있는 조건과 서술형으로만 있는 조건의 비율. Q4의 근거가 된다.
- 임시 사용자 유형 3개로 나이·지역·소득 필터를 걸었을 때 남는 건수. Q3의 근거가 된다.
- 마감 정책 비율, 서술형 필드 길이 분포.
- 온통청년과 복지로의 겹침률. 정책명을 정규화해 맞춘다.

**W5 코드 필터와 의미 검색 비교.** 테스트 질문 20~30개를 만들고 질문마다 정답 정책을 붙인다. 두 방식을 비교한다.
1. LLM이 질문을 온통청년 분류·키워드 코드로 바꿔 거른다.
2. 임베딩으로 비슷한 정책을 찾는다. 임베딩은 파일로 두고 메모리에서 비교한다.

상위 10개 안에 정답이 몇 개 들어오는지 본다. 차이가 작으면 의미 검색을 빼고, 크면 넣는 쪽으로 Q8에 올린다. 어느 쪽이든 자격 판정은 코드 필터가 먼저 하고, 의미 검색은 남은 후보의 순위만 정한다. 외부 임베딩 API에 사용자 문장을 보내는 실험은 하지 않는다. 테스트 질문은 직접 만든 문장이다.

**W6 토큰 측정.** D1에 따라 LLM이 받는 양은 API 응답 크기가 아니라 서버가 넘기기로 한 정책 수와 필드가 정한다. 그래서 "API별 소모량" 대신 "넘길 필드 기준 정책 1건당 토큰"을 잰다. [context-measurement](../context-measurement/README.md)의 T4를 이 범위로 줄이자는 안이 Q1에 올라가 있다.

## 지키는 것

- 복지로 중앙부처는 반복 호출하지 않는다. W2에서 받은 샘플만 쓴다.
- 샘플은 공개 데이터지만 요청 URL은 저장하지 않는다. URL에 키가 들어 있다.
- 공공 API 실제 호출은 사람이 실행한다(AGENTS.md "API 키").
