# 법률 정보 에이전트 토큰 측정

Q7(컨셉 확정)의 조건을 확인하는 실험이다. [3안 비교](../../docs/reference/concept-comparison.md) 2.1에서 법률 정보안은 질문당 15K~40K 토큰, 하루 5~13개 질문으로 **추정**했다. 이 스크립트는 그 값을 실제로 잰다. 확정 기준은 무료 Groq 하루 200K 토큰으로 **하루 30개 질문 이상**이다.

## 무엇을 하나

제안서 5.1의 흐름을 작게 재현한다. LLM이 도구 두 개를 골라 부르는 루프를 돌리고, 호출마다 Groq가 돌려준 `usage`를 더한다.

| 도구 | 하는 일 | 국가법령정보 API |
| --- | --- | --- |
| `search_law` | 목록 검색, 최대 5건 | `lawSearch.do` |
| `get_law` | 본문 조회. 법령은 조문 하나만 지정할 수 있다 | `lawService.do` |

자료 종류(target)는 `lstrm`(법령용어), `law`(현행 법령), `school`(학칙·학교규정), `admrul`(행정규칙), `moelCgmExpc`(고용노동부 해석), `expc`(법령해석례), `prec`(판례)다. 질문은 제안서 7.1 사례에서 6개를 골랐다(용어 1, 학사 1, 노동 2, 주거 1, 교통 1).

조절값:
- `--max-steps` (기본 6): 질문당 LLM 호출 상한. 마지막 호출에서는 도구를 끄고 답을 강제한다. 결과에 `forced`로 남는다.
- `--max-chars` (기본 3000): 도구 결과 하나를 LLM에 넘길 최대 글자 수. 토큰을 가장 크게 좌우할 값이다.

이 두 값을 바꿔 돌리면 결과가 `results/<도구 버전>-steps<N>-chars<M>/`에 따로 쌓여 비교할 수 있다. 도구 설명이나 루프를 고치면 `trial.py`의 `TOOL_VERSION`을 올려 이전 결과를 덮지 않는다.

## 실행

준비:
1. `.env`에 `GROQ_API_KEY`와 `LAW_API_OC`를 넣는다. 이름은 `.env.example`에 있다. Groq 키 발급은 청년 정책 브랜치(`claude/exciting-goldberg-y71yhi`)의 `experiments/api-survey/api-keys.md` "2-1"과 같다.
2. 국가법령정보 공동활용(open.law.go.kr)에서 `법령`, `법령용어`, `학칙·공단·공공기관`, `행정규칙`, `고용노동부 법령해석`, `법령해석례`, `판례`의 OPEN API 활용을 신청한다. 신청할 때 호출할 PC의 IP나 도메인을 등록해야 할 수 있다(확인하지 않음). 승인되지 않은 자료는 `[API 오류]`로 LLM에 전달되고, 그 사례의 토큰은 실제보다 적게 나온다.

저장소 루트에서:

```bash
python3 experiments/legal-tokens/trial.py --fake
```

키 없이 흐름만 확인한다. 결과는 임시 폴더에 쓰고 저장소는 건드리지 않는다.

```bash
python3 experiments/legal-tokens/trial.py
```

기본 모델(`gpt-oss-120b`)로 6개 사례를 돌린다. Windows는 `py experiments/legal-tokens/trial.py`.

```bash
python3 experiments/legal-tokens/trial.py --models gpt-oss-20b,qwen3.8-27b --max-chars 1500
```

모델과 조절값을 바꿔 돌린다.

```bash
python3 experiments/legal-tokens/trial.py --report
```

저장된 결과로 요약만 다시 본다.

## 한도와 호출 수

- Groq 무료 한도는 분당 8K 토큰, 하루 200K 토큰이다(청년 정책 브랜치 `comparison.md`, 공식 표). 도구 결과가 쌓이면 호출 하나가 수천 토큰이라 429가 자주 난다. 스크립트가 `retry-after`만큼 기다리므로 6개 사례에 수십 분 걸릴 수 있다.
- `--budget`(기본 150,000)을 넘으면 그 모델은 멈춘다. 하루 한도를 다 쓰지 않게 하려는 값이다. 다음 날 다시 실행하면 저장되지 않은 사례부터 이어서 한다.
- 법령 API 응답은 `cache/`에 저장하고 같은 요청은 다시 보내지 않는다. 모델이나 조절값을 바꿔 다시 돌려도 법령 API 호출은 거의 늘지 않는다.

## 결과와 커밋

- `results/`에는 질문, 호출마다의 `usage`, 도구 인자와 결과 글자 수, 최종 답이 있다. `cache/`에는 공개 법령 원문이 있다. 키는 저장하지 않는다.
- 법령 API 응답의 링크에는 OC 값이 들어 있다. 스크립트가 저장 전과 LLM에 넘기기 전에 `OC={LAW_API_OC}`로 바꾼다. 커밋 전에 OC 값으로 한 번 검색해 확인한다.
- 둘 다 커밋해서 공유한다. 다음 사람이 `--report`로 같은 숫자를 볼 수 있다.

## 읽는 법

`--report`는 모델·조절값마다 질문당 평균·중앙값·최대 토큰과 하루 질문 수를 보여 준다. 판단할 때는 다음도 함께 본다.

- `forced` 사례가 많으면 단계 상한이 낮아 토큰이 실제보다 적게 나온 것이다.
- `[API 오류]`나 `검색 결과 0건`이 많으면 답의 품질과 토큰이 모두 실제와 다르다. 결과 파일의 도구 기록에서 확인한다.
- 답의 품질은 이 스크립트가 채점하지 않는다. 결과 파일의 `answer`를 사람이 읽는다.

## v4: API 하나, LLM 2회 (`two_call.py`)

v3 결과로 범위를 줄였다(PM 결정, 2026-11-01). 노동·주거 두 분야, 국가법령정보 `law`(현행 법령 본문) 하나만 쓴다. 검색 도구를 없애고 청년 정책 D3와 같은 2회 구조로 바꿨다.

| 단계 | 하는 일 | 법령 API |
| --- | --- | --- |
| 준비 | 근로기준법·최저임금법·주택임대차보호법·민법(임대차 제618~654조)의 전체 본문을 한 번 받아 `laws/`에 조문 단위로 저장 | 법령마다 2회, 처음 한 번만 |
| 1회차 LLM | 조문 목차(번호·제목)를 보고 조문을 최대 3개 고른다. 의도와 되물을 정보도 함께 JSON으로 | 없음 |
| 서버 | 고른 조문 원문을 `laws/`에서 꺼낸다 | 없음 |
| 2회차 LLM | 그 조문만으로 답한다. 서버가 답에 인용된 "제N조"가 넘겨준 조문인지 검사한다 | 없음 |

사례는 v3의 노동·주거 3개(c03~c05)에 4개를 더한 7개다.

```bash
python3 experiments/legal-tokens/two_call.py --fake
```

```bash
python3 experiments/legal-tokens/two_call.py
```

```bash
python3 experiments/legal-tokens/two_call.py --toc domain
```

`--toc domain`은 사용자가 첫 화면에서 분야 버튼(아르바이트·월세)을 눌렀다고 보고 그 분야 목차만 넣는다. 1회차 토큰이 얼마나 주는지 본다. 결과는 `results-two-call/`(v4 때 이름 `results-v4/`), 법령 원문은 `laws/`에 저장된다. 둘 다 커밋한다.

요약에서 볼 것:
- 질문당 토큰과 하루 질문 수.
- 고른 조문의 제목. 질문에 맞는 조문인지 사람이 본다(c03이면 근로기준법 제54조 휴게).
- "넘겨주지 않은 조문 인용"이 있으면, 넘겨준 원문 밖의 조문 번호를 답에 쓴 것이다. 법령명까지는 맞춰 보지 않는다.

## v5: 주제→조문 표 (`two_call.py --topics`)

v4에서 놓친 조문 3건(주휴수당의 근로기준법 제18조③, 퇴직 후 임금의 제36조, 보증금 반환의 주택임대차보호법 제4조②)은 모두 조문 제목만으로는 질문과 이어지지 않는 경우였다. v5는 자주 묻는 주제 24개와 근거 조문을 묶은 [topics.json](topics.json)을 1회차에 함께 준다.

- 1회차: LLM이 주제를 0~2개 고르면 서버가 그 주제의 조문을 넣는다. 부족하면 목차에서 조문을 2개까지 더 고른다. 한 질문에 조문은 최대 4개.
- 2회차: v4 규칙에 두 가지를 더했다. 준 조문에 없는 시간·금액·기간 기준을 기억으로 채우지 않는다. 절차 질문에는 신고처·서류·기관 이름을 쓰지 않고 "관할 기관의 공식 안내에서 확인 필요"라고 쓴다.
- 사례 5개를 더했다(c11~c15). 주제 표를 만든 뒤에 쓴 질문이다. c15(일하다 다침)는 표에 없는 주제라 목차에서 근로기준법 제78조(요양보상)를 찾아야 한다.
- 표의 조문 번호는 `laws/` 원문 제목으로 확인했다. 표에 없는 조문이 있으면 스크립트가 시작할 때 멈춘다.

```bash
python3 experiments/legal-tokens/two_call.py --topics
```

```bash
python3 experiments/legal-tokens/two_call.py --topics --toc domain
```

`--toc fallback`(v5 실행 뒤 추가): 1회차에 주제 표만 주고, 맞는 주제가 없을 때만 목차로 한 번 더 고른다. 1회차가 목차 전체(약 5,000토큰)에서 주제 표(2,182자)로 줄어든다. 표에 없는 질문만 LLM 3회가 된다.

```bash
python3 experiments/legal-tokens/two_call.py --topics --toc fallback
```

Groq가 60~90초보다 오래 기다리라고 하면(하루 한도에 닿은 것으로 본다) 스크립트가 기다리지 않고 멈춘다. 다음 날 같은 명령을 다시 실행하면 저장되지 않은 사례부터 이어서 한다.

v4와 비교하려면 새 사례(c11~c15)도 v4로 돌린다. 이미 돌린 사례는 건너뛴다.

```bash
python3 experiments/legal-tokens/two_call.py
```

읽을 때 주의:
- 주제 표에 기존 7개 사례의 답이 들어 있다. 그 7개의 조문 선택 개선은 낙관적인 값이다. c11~c15를 따로 본다.
- v5는 주제 표와 2회차 규칙을 함께 바꿨다. 토큰 변화는 주로 주제 표(약 1,900자)에서, 답의 "지어낸 절차" 변화는 주로 2회차 규칙에서 온다고 보지만 나눠 재지는 않는다.

## 실행 기록

### v1 (2026-10-31, gpt-oss-120b, 단계 6, 본문 3,000자)

**측정값으로 쓰지 않는다.** 6개 사례 중 법령 본문을 실제로 읽은 사례가 없다. 숫자(답을 낸 3건 평균 3,448토큰)는 본문이 입력에 들어가지 않은 상태의 값이라 실제보다 작다.

- 목록 검색은 기본으로 법령명만 본다. "근로기준법 휴게시간"처럼 낱말을 여러 개 넣은 검색 16회 중 15회가 0건이었다. "근로기준법" 하나만 넣은 검색만 결과가 나왔다.
- 모델이 본문 조회 id를 지어냈다(`3070000`, `0000000000`, `민법`). 모두 "일치하는 법령이 없습니다"였다.
- 마지막 단계에서 `tool_choice: none`을 보냈는데 gpt-oss가 도구를 불러 Groq가 400을 돌려줬다(c03, c04, c06).
- c01은 빈 답이었다. c05는 본문을 읽지 못했는데 "민법 제618조(임대인의 의무)"를 인용했다. 임대인의 의무는 민법 제623조이고 인용 문구도 원문과 다르다(원문 대조는 사람이 다시 확인). 근거 검증 없이 답하면 조문을 지어낸다는 실례다.

v2에서 고친 것: 검색 도구 설명에 "이름 하나로 찾는다"와 본문 검색(`body_search` → `search=2`)을 넣었다. 0건이거나 id가 틀리면 다시 시도하라는 안내를 돌려준다. 마지막 단계에서는 도구 정의를 아예 뺀다. 빈 답은 `empty`로 따로 센다. 요약에 "본문 확보" 횟수와 유효 사례(답을 냈고 본문을 1번 이상 읽음)만의 평균을 넣었다.

### v2 (2026-10-31, gpt-oss-120b, 단계 6, 본문 3,000자)

**이것도 측정값으로 쓰지 않는다.** 본문을 실제로 읽은 사례가 1건(c04)뿐이고, 그것도 엉뚱한 법령이었다.

- 스크립트 버그. 검색 결과가 0건일 때 응답 머리(`resultCode` 등)를 결과 1건으로 넘겼다. 그래서 0건 재시도 안내가 한 번도 나가지 않았고, 모델은 아무것도 못 찾은 채 답했다. v1의 "검색 결과 0건"도 같은 이유로 나오지 않았다.
- 목록의 `id` 필드는 순번이다. c04는 이 순번 `1`을 법령ID로 넣어 「재외국민…」 법령 본문을 받았다.
- 숫자는 아래 한계(하한)로만 읽는다. 답을 낸 6건 평균 6,791토큰, 하루 약 29개로 이미 목표 30개 아래다. 본문을 제대로 읽으면 입력이 늘어난다(추정). 다만 검색이 한 번에 맞으면 헛도는 호출이 줄어 반대로 작아질 수도 있다.
- 답의 품질. 본문을 읽지 않고 조문을 인용한 답이 4건이다. 이 중 확인한 2건이 틀렸다. 휴게시간을 근로기준법 제53조로 인용했고(휴게는 제54조), 민법 제618조를 다시 임대인의 의무로 인용했다(제623조). c06은 같은 낱말을 수백 번 반복하는 출력으로 끝났다.

v3에서 고친 것: 검색 응답에서 결과 항목만 꺼내 0건을 제대로 판정한다(저장된 실제 응답 33건으로 확인). 목록에서 순번 `id`와 링크를 뺀다.
