# D10. 자격 판단은 혼합(서버가 코드, LLM이 서술형)으로 하고, LLM에 보내는 선택지 값을 늘린다

> [결정 기록 인덱스](README.md) · 승인: 2026-11-08 PM · 원래 Q4

**정할 것**: 서술형 자격 조건을 누가 판단하나(Q4), 그리고 그러려면 LLM에 어떤 사용자 값을 보내나(개인정보, AGENTS.md)

**검토한 선택지**: [Q4 실험](../../experiments/context-measurement/q4-judgement.md)
- 판단 주체: LLM 단독 / 사용자 단독(원문 보여 주기) / 혼합
- LLM에 보내는 값: 가. 선택지 값을 늘린다 / 나. 지금처럼 나이·지역·취업 상태만

**결정**: 혼합 + 가.

**판단 방식(혼합)**:
1. 서버가 코드 요건을 판정한다. 학력·혼인·취업 요건 목록에 사용자 값이 없으면 "불가", 특화 요건(여성·수급자 등)이 있으면 "확인 필요". LLM에 맡기지 않는다.
2. LLM(D7)이 서술형 조건을 읽는다. 신청 주체(개인인지 기업인지), 추가 자격, 참여 제한, 소득 기타 조건. 판단할 수 없으면 사용자에게 물을 질문을 만든다.
3. 사용자에게 판정과 근거를 함께 보여 준다. "신청할 수 있어 보여요 / 확인이 필요해요(질문) / 해당되지 않아요(이유)" + 원문 조건 + 신청 링크. 최종 자격은 운영 기관이 정한다고 안내한다.

**LLM에 보내는 사용자 값(가)**: 기존(나이, 지역, 취업 상태)에 더해 **소득 구간, 주택 여부, 학력, 가구원 수**.
- 모두 **선택지로만** 받는다. 금액·주소·자유 입력은 받지 않는다. 제안서의 "선택지로 받은 값만 LLM에 보낸다"는 원칙은 그대로다.
- 서버에 저장하거나 로그에 남기지 않는다(AGENTS.md "개인정보" 그대로).
- 공공 API 검색어에는 넣지 않는다. 서버 필터와 LLM 판단에만 쓴다.

**이유**: 실험에서 LLM 단독은 14건 중 6건 일치, 신청 못 하는 정책을 "가능"이라 한 것이 2건이었다. 둘 다 코드 요건을 잘못 읽은 경우라, 서버가 코드를 판정하는 혼합에서 8건 일치, 0건이 됐다(실측, 표본 14건). 가안은 이 실험과 같은 조건이라 품질을 쟀다.

**구현 때 시험할 것**: LLM의 "불가"를 신청 주체가 기업·기관이거나 원문이 분명히 배제할 때로 줄이기. 중위소득 기준표(가구원 수별)를 LLM에 함께 주기.

**다시 볼 때**: "가능"이라 했는데 신청이 안 되는 사례가 나올 때. 선택지 값을 더 늘려야 할 때(그때 다시 PM 승인).
