# D8. API 한도는 키 돌려 쓰기 대신 각자 키·캐시·운영계정으로 푼다

> [결정 기록 인덱스](README.md) · 승인: 2026-11-08 PM · 원래 Q 번호 없음(PM과 대화 중 결정)

**정할 것**: Groq·공공데이터포털 호출 한도가 모자랄 때 어떻게 늘릴지

**검토한 선택지**:
1. 팀원 계정 키를 여러 개 모아 서버에서 돌려 쓴다
2. 개발은 각자 키, 서비스는 키 하나 + 응답 캐시 + 넘길 건수 줄이기, 시연 전 공공데이터포털 운영계정 신청, Groq는 모자라면 유료 플랜(PM 승인)

**결정**: 2.
- **개발**: 팀원마다 자기 계정 키를 자기 로컬 `.env`에 넣고 자기 개발·테스트에만 쓴다.
- **서비스**: 서비스 키는 하나만 둔다. 공공 API 응답을 서버 메모리에 짧게 캐시해 같은 요청을 다시 부르지 않는다. LLM에 넘기는 정책 수는 순위 기준(Q3)으로 줄인다.
- **시연 전**: 공공데이터포털 운영계정을 신청한다(활용 사례 등록).
- **Groq 한도가 그래도 모자라면**: 유료 Developer 플랜을 PM 승인을 받아 쓴다.

**캐시의 개인정보 조건** (AGENTS.md "개인정보"):
- 캐시 키는 공공 API에 보내는 요청값(시군구 코드, 정책 대분류, 페이지)만 쓴다. 나이·소득처럼 서버가 응답을 받은 뒤 거르는 값은 키에 넣지 않는다.
- 서버 메모리에만 두고, 파일·DB·로그에 쓰지 않는다. 짧은 만료 시간을 둔다.
- 이 조건으로 구현이 안 되면 다시 PM 승인을 받는다.

**이유**: 한도를 피하려고 계정 여러 개를 돌려 쓰는 것은 대부분의 API 약관이 금지한다(Groq·공공데이터포털 약관 조항은 직접 확인하지 않음). 걸리면 시연 중 키가 막힐 수 있다. 정식 경로(운영계정, 유료 플랜)와 호출·토큰 자체를 줄이는 방법(캐시, Q3)이 더 안전하다.

**다시 볼 때**: Groq 콘솔에서 확인한 무료 한도로 계산했을 때, 캐시와 Q3을 적용해도 시연 규모를 감당하지 못할 때.
