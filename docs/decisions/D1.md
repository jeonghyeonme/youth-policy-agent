# D1. 공공 API 데이터는 미리 전부 수집해 JSON 파일로 두고, 서버는 실행 중에 공공 API를 부르지 않는다

> [결정 기록 인덱스](README.md) · 승인: 2026-10-29 PM · 원래 Q7(검토 중 제안, STATUS에는 올리지 않음) · 근거 자료: [api-survey 확인 결과](../../experiments/api-survey/findings.md) · [log/002](../log/002.md)

**정할 것**: 사용자가 질문할 때마다 공공 API를 부를지, 데이터를 미리 받아 두고 서버가 그 안에서 찾을지.

**검토한 선택지**:
1. 실시간 호출. 조건이 모이면 서버가 그때 공공 API를 부른다(제안서 원래 흐름).
2. 전부 미리 수집. 수집 스크립트가 주기적으로 받아 JSON 파일로 저장하고, 서버는 파일만 읽는다.
3. 섞기. 목록은 미리 수집하고, 서술형 자격조건이 있는 상세는 후보 몇 건만 그때 부르고 저장한다.

**결정**: 2번. 저장은 JSON 파일로 하고, 따로 운영하는 DB 서버는 두지 않는다.

**이유**:
- 복지로 두 API는 목록 응답에 자격조건이 없다. 선정기준과 지원대상은 상세 조회에만 있다(Swagger 명세 확인). 실시간으로 하면 질문 하나에 목록 1회와 상세 N회가 든다. 복지로 중앙부처 개발계정 한도는 하루 100이다.
- 데이터가 작다. 온통청년 3,981건, 복지로 중앙부처 461건(파일 데이터 메타 정보 기준)에 지자체·잡알리오·LH 공고를 더해도 수천~1만 건이다. 서버가 메모리에 올려 나이·지역·소득으로 걸러도 충분하다(추정).
- 서버는 데이터를 읽기만 한다. 사용자 정보를 저장하지 않으므로 서버가 쓰는 데이터가 없다. 쓰는 쪽은 수집 스크립트 하나다.
- 실행 중에 외부 호출이 없으니 한도·지연·장애 걱정이 없고, 테스트도 같은 파일로 매번 같은 결과를 낸다.
- 3번은 첫 수집이 빠르지만 움직이는 부분이 가장 많다. 복지로 수집이 한도에 막힐 때의 대안으로 둔다.

**따라오는 것**:
- 제안서 "서비스 흐름"의 "조건이 모이면 서버가 API를 호출" 단계는 "서버가 수집해 둔 데이터에서 찾는다"로 바뀐다.
- 복지로 중앙부처 461건을 모두 상세 조회하면 하루 100건 한도로 최소 5일이 걸린다(계산). 한도를 기능(목록·상세)별로 세는지 키 전체로 세는지는 확인하지 않았다. 청년 대상만 받으면 건수는 줄어든다.

**다시 볼 때**:
- 호스팅(Q6)이 실행 중 파일 교체를 막을 때. 서버리스 환경에서는 데이터 갱신이 재배포가 된다. 그러면 저장 방식을 다시 정한다.
- 조회가 복잡해질 때. 별도 서버가 필요 없는 SQLite로 먼저 옮긴다.
- 의미 검색을 넣기로 할 때(Q8). 임베딩도 처음에는 파일로 둔다.
- 데이터가 메모리에 다 올라가지 않을 만큼 커질 때.
