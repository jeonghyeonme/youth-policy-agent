# 후보 컨셉 분석 — 대학생·사회초년생 법률 정보 에이전트

> [문서 지도](../README.md) · 작성: 2026-10-31 (AI 분석, PM 검토 전) · 원문: 「대학생·사회초년생을 위한 법률 상담 및 법률 정보 제공 에이전트 제안서」 PDF 17쪽(저장소 밖에서 공유)
>
> 컨셉 확정용 3안 비교(청년 정책 / 생필품 가격 / 법률 정보)의 첫 단계. 이 문서는 법률 정보안만 다룬다. 채택 여부는 PM이 정한다.

## 1. 한 줄 요약

대학생·사회초년생이 일상어로 물으면, LLM이 **질문 의도(개념 / 내 상황 적용 / 절차)**를 구분해 **국가법령정보 공동활용 API** 등 공식 원문을 여러 번 찾아보고, 출처·시행일을 붙여 답하는 대화형 에이전트.

## 2. 제안서 내용 정리

### 2.1 질문 유형 → 응답 경로

| 유형 | 예 | 답변 구성 |
| --- | --- | --- |
| 개념·단순 정보 | "주휴수당이 뭔가요?" | 쉬운 설명 → 예시 → 출처 |
| 개인 상황 적용 | "제 근무 형태에도 적용되나요?" | 적용 가능성 → 조건·근거 → 미확인 사항 |
| 절차·행동 안내 | "밀린 임금 받으려면 어디에 뭘 내나요?" | 절차 → 준비 자료 → 접수 경로 → 출처 |

추가 질문은 "답이 실질적으로 바뀔 때만" 한다(근무처·학교명을 일괄로 묻지 않음).

### 2.2 분야와 우선순위

| 우선순위 | 분야 | 평가셋 비중 |
| --- | --- | --- |
| 높음 | 생활법령·법률용어, 대학생활·학사 규정 | 66.7% (40/60) |
| 중간 | 도로교통, 노동·아르바이트 | 20.0% (12/60) |
| 낮음 | 소비자·개인정보, 주거·임대차, 기타 민형사 절차 | 13.3% (8/60) |

부가 기능: 법령 개정 전후 비교(평가셋 60개 중 3개, 교차 태그).

### 2.3 데이터·API

| 출처 | 형식 | 비고 |
| --- | --- | --- |
| 국가법령정보 공동활용 OPEN API (`law.go.kr/DRF/lawSearch.do`, `lawService.do`) | JSON/XML/HTML | 키(OC) 하나로 target만 바꿔 여러 자료 조회. target별 공동활용 승인 필요 |
| ├ 법령용어 `lstrm` · 학칙·학교규정 `school` · 시행일 기준 법령 `eflaw` | | 높음 |
| ├ 행정규칙 `admrul` · 고용노동부 법령해석 `moelCgmExpc` | | 중간 |
| └ 자치법규 `ordin` · 판례 `prec` · 법령해석례 `expc` · 변경이력 `lsHstInf`/`lsJoHstInf` · 신구법 `oldAndNew` | | 낮음 |
| 생활법령정보 조회 서비스 (공공데이터포털) | SOAP/XML | 별도 활용신청. **개발계정 하루 100건** |
| 찾기쉬운 생활법령정보 웹, 대학 규정집·학사 공고, 고용노동부·경찰청·법원 안내 | HTML/PDF | API 없음 → 웹 검색·크롤링·PDF 추출 |

### 2.4 구조·기술

- 흐름: 의도·분야·시점 파악 → 필요 시 추가 질문 → API/웹 탐색(결과 보고 다음 탐색 선택) → 근거·출처·날짜 검증 → 답변 또는 재검색/추가 질문
- 도구 10종: 현재 시각, 법령·규정 검색, 본문 조회, 법률용어, 시점·변경이력, 개정 비교, 판례·해석, 웹 검색, 웹/PDF 본문, 금액·기간 계산
- 스택: Python·FastAPI, LangChain, LangGraph(체크포인터), HTTPX·HTML 파서·PDF 추출, SQLite(대화·근거·평가 기록), 모바일 웹 채팅 UI, pytest
- 벡터 DB·임베딩·다중 에이전트는 초기에 두지 않음. LLM 업체·모델 미정
- 평가: 평가셋 60개(단순 30 / 적용 18 / 절차 12), 지표 9개, 사용자 6~10명 사용성 평가
- 일정: **6주**

## 3. 에이전트 개발 가능성 판단

**결론: 기술적으로 가능하고, "에이전트"라는 형식에는 3안 중 가장 잘 맞는다. 다만 제안서 범위 그대로는 우리 일정(4~5주, D1)에 비해 크고, 법적·개인정보 위험을 먼저 정리해야 한다.**

### 3.1 강점

| 항목 | 내용 |
| --- | --- |
| 에이전트 적합성 | 의도 분기, 다단계 탐색(목록→본문→이력→해석), 근거 부족 시 재검색 — 도구 호출 루프가 필요한 문제다. 단일 API 조회 후 요약하는 구조보다 LLM이 하는 일이 분명하다 |
| 데이터 접근성 | 국가법령정보 API는 무료이고 JSON을 주며, 키 하나로 용어·법령·학칙·판례·해석을 모두 조회한다 |
| 니즈의 넓이 | 아르바이트 임금, 월세 수선비, 학사 규정, 교통 규칙 등 대상 사용자가 실제로 겪는 문제가 많다 |
| 기획 완성도 | 질문 유형·분야 우선순위·도구 목록·오류 처리·평가셋 배분·주차별 일정까지 구체적이다 |
| 차별점 | 출처·시행일·현행/연혁 구분을 답변에 붙이는 것 — 일반 챗봇 대비 설명 가능한 차이 |

### 3.2 위험과 확인할 것

| # | 위험 | 영향 | 대응 방향 |
| --- | --- | --- | --- |
| R1 | **"법률 상담" 표현과 변호사법**: 개인 사건에 대한 법적 판단을 주면 비변호사 법률사무 문제로 비칠 수 있다 | 높음 | 명칭을 "법률 정보 안내"로, 개인 상황 적용은 "조건과 근거 제시"까지만. 면책 문구. 제안서도 확정 결론을 내지 않는다고 적고 있어 방향은 맞다 |
| R2 | **환각의 피해가 크다**: 틀린 가격보다 틀린 법 안내가 더 해롭다 | 높음 | 제안서의 원문 인용 검증·미확인 표시를 핵심 기능으로 유지. 평가에서 "존재하지 않는 출처 인용"을 중대 오류로 집계(제안서 8.2에 있음) |
| R3 | **범위가 크다**: 분야 7개, API 11종+웹 검색+PDF, 개정 비교, LangGraph 상태 관리를 6주에 잡았다. 우리 실질 개발은 4~5주 | 높음 | 높음 우선순위(생활법령·용어·학사 규정) + 노동 하나로 축소. 개정 비교·판례·자치법규는 확장으로 |
| R4 | **개인정보 규칙과 충돌**: 6.3에서 SQLite에 "대화" 기록, 6.2에서 "사용자 제공 사실"을 상태에 저장. AGENTS.md는 대화·선택값을 DB에 남기는 코드를 금지한다. 법률 질문은 임금체불·월세 분쟁처럼 민감한 내용이 많다 | 높음 | 대화는 세션 메모리에만, 평가 기록은 가상 질문만. 학교명·지역을 LLM에 보내는 것도 PM 승인 대상 |
| R5 | **대학 규정 커버리지**: `school` target의 학교별 수록 여부·연혁 범위가 다르다고 제안서도 적었다. 학사 공고·강의계획서는 학교마다 웹 구조가 달라 크롤링 비용이 크다 | 중간 | 1주 차에 목표 대학 몇 곳의 수록 여부를 실제 응답으로 확인. 시연 대학을 1~2곳으로 한정 |
| R6 | **웹 검색 API가 새 외부 서비스**: 업체 미정, 유료일 수 있다 | 중간 | PM 승인 대상. 초기엔 공식 도메인 직접 조회만으로 시작 가능한지 검토 |
| R7 | **생활법령정보 조회 서비스 하루 100건** | 낮음 | 응답 캐시·샘플 저장(AGENTS.md 트래픽 원칙과 같음). 웹 콘텐츠로 대체 가능 |
| R8 | **정답 검증 능력**: 팀원 2인 교차 검토뿐, 법률 전문가 검증 없음 | 중간 | 평가 대상을 "원문과 일치하는가"로 한정. 제안서도 전문가 검증으로 표시하지 않는다고 적었다 |
| R9 | **API 승인 대기**: target별 공동활용 승인이 늦으면 1주 차가 막힌다 | 중간 | 제안서 대응(공개 웹자료로 개발용 응답) 유지. 신청은 컨셉 확정과 무관하게 먼저 해 둘 수 있다 |

### 3.3 제안서 자체에서 고칠 점

- **API 인증값이 본문에 들어 있다.** 4.2절 예시 URL마다 `OC=` 값이 실제 값으로 적혀 있다. OC는 국가법령정보 API의 사용자 식별값이라 키와 같이 다뤄야 한다(AGENTS.md "API 키"). 이 문서에는 옮기지 않았다. 저장소에 PDF나 예시를 넣을 때는 `OC={LAW_API_OC}`처럼 환경변수 이름으로 바꾼다. 이미 공개된 곳에 공유했다면 재발급을 검토한다.
- 제목의 "법률 상담"과 본문의 "확정 결론을 내지 않는다"가 어긋난다(R1).
- 일정 6주 ↔ 팀 제약 4~5주(D1).
- SQLite 대화 기록 ↔ 개인정보 규칙(R4).

## 4. 3안 비교에 넘길 값

비교 기준을 맞추기 위해 이 안을 다음과 같이 요약해 둔다. 점수는 비교 단계에서 다른 두 안과 함께 매긴다.

| 기준 | 법률 정보안 |
| --- | --- |
| 대상 사용자 | 대학생·사회초년생 (청년 정책안과 겹침) |
| 니즈 빈도 | 사건이 생길 때 집중적으로(아르바이트·월세·학사). 매일 쓰는 서비스는 아님 |
| 니즈 강도 | 높음 — 돈·권리가 걸린 문제, 기존 정보가 어렵고 흩어져 있음 |
| 에이전트 필요성 | 높음 — 다단계 탐색·의도 분기·근거 검증 |
| 데이터 | 무료 공식 API 다수, 학교 규정은 일부 웹/PDF |
| 구현 난이도 | 높음 — 도구 10종, 상태 그래프, 원문 검증 |
| 4~5주 실현성 | 범위 축소 시 가능 |
| 주요 위험 | 법적 책임 인식, 환각 피해, 민감 대화 |
| 기획 성숙도 | 높음 — 평가셋·일정·도구 정의까지 있음 |

## 5. 채택 시 PM 승인이 필요한 항목

채택이 정해지면 STATUS "PM 승인 대기"에 올릴 후보(지금은 올리지 않는다 — 컨셉 미확정).

1. 컨셉 변경(D1 재검토) 및 활용 API: 국가법령정보 공동활용 API, 생활법령정보 조회 서비스
2. 웹 검색 API 도입 여부·업체
3. 기술 스택: Python·FastAPI·LangChain·LangGraph·SQLite (현 Q6)
4. 학교명·지역·사건일을 LLM에 보내는지, 대화를 저장하는지(현 개인정보 규칙의 예외인지)
5. 서비스 명칭("상담" 사용 여부)과 면책 문구
6. 범위 축소안(분야·기능)과 4~5주 일정
