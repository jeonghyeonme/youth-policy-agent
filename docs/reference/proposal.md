# 생필품 가격 에이전트 제안서

Oct 18, 2026 · @박정현

> 2026-10-30, 컨셉 변경([D1](../decisions/D1.md))에 따라 원문을 생필품 가격 에이전트 제안서로 바꿨습니다. 이전 제안서(청년 정책 안내 에이전트)는 `archive/youth-policy` 브랜치에 있습니다.

## 개요

사용자가 채팅으로 물으면 LLM이 질문을 해석해 한국소비자원 참가격 생필품 가격 정보 API를 호출하고, 필요한 가격 정보를 돌려주는 웹 서비스입니다. 타깃 사용자와 구체 기능은 API 데이터를 분석한 뒤 정합니다.

- 데이터: 참가격 생필품 가격 정보 (전국 주요 유통업체 가격을 매주 조사)
- 형태: 회원 정보를 저장하지 않는 웹 채팅 서비스
- 타깃 사용자: 미정 (데이터 분석 뒤 결정)

## 배경

- **기존 서비스**: [참가격](https://www.price.go.kr/tprice/portal/main/main.do) 사이트에 이미 장바구니가격비교 메뉴가 있습니다.
- **판매점 분포**: 대부분 대형마트이고 편의점은 거의 없습니다(참가격 판매점 목록 기준, 정확한 업태별 수는 미확인).
- **데이터로 할 수 있는 것**: 상품에 용량과 단위량이 있어 개당·100g당 단가를 비교할 수 있고, 가격에는 할인 여부·기간과 1+1 여부, 판매점에는 좌표가 있습니다.

## 서비스 흐름

> 원문의 흐름 다이어그램은 내보내기에서 빠져 글로 옮겼습니다.

1. 사용자가 채팅으로 질문합니다.
2. LLM이 의도를 해석합니다.
3. 필요한 조건이 다 있는지 판단합니다. 없으면 선택지로 조건을 받고 2로 돌아갑니다.
4. 조건이 다 있으면 서버가 공공 API를 호출합니다.
5. 서버가 응답을 조건으로 필터링합니다.
6. LLM이 결과로 답변하고, 사용자는 다음 질문을 이어 갑니다.

필요한 조건이 모일 때까지 선택지로 묻고, 조건이 다 모이면 서버가 참가격 API를 호출해 결과를 걸러 LLM이 설명합니다. 서버가 걸러내거나 계산할 내용(단가 비교, 총액 등)은 타깃이 정해진 뒤 정합니다.

## 사용자 시나리오

타깃이 아직 정해지지 않아, 데이터로 가능한 방향별로 시나리오 세 개를 후보로 둡니다. 데이터 분석 결과에 따라 하나를 고르거나 합칩니다.

### 시나리오 1. 주말 장보기를 한 곳에서 끝내고 싶은 직장인

**상황**: 자취하는 직장인이 토요일에 장을 보려 합니다. 우유, 라면, 세제를 한 매장에서 다 사고 싶고, 1+1 행사가 있으면 그쪽으로 가고 싶습니다.

> 사용자: 우유 1L 두 개, 신라면 한 묶음, 세탁세제 하나 사려고. 한 곳에서 다 살 수 있는 데 중에 제일 싼 곳 알려줘.
>
> 에이전트: 우유는 브랜드가 여러 개예요. 서울우유, 매일우유, 상관없음 중에 골라주세요.
>
> 사용자: 서울우유.
>
> 에이전트: 세 상품 가격이 모두 있는 매장 중 총액이 가장 낮은 곳은 A마트(○○원)이고, 세제가 1+1이라 실질 단가가 가장 쌉니다. 10월 ○일 조사 기준이에요.

**에이전트가 하는 일**: 상품명을 상품 ID로 확정하고, 모호하면 선택지로 되묻습니다. 판매점별 가격을 조회해 세 상품이 모두 있는 매장만 남기고, 1+1과 할인을 반영한 총액으로 비교합니다.

**데이터 한계**: 세 상품이 모두 조사된 매장이 충분한지 확인해야 합니다. 가격은 조사일 기준이라 당일 가격과 다를 수 있습니다.

### 시나리오 2. 사무실 탕비실 소모품을 사는 총무 담당자

**상황**: 20명 규모 사무실의 총무 담당자가 한 달 치 소모품을 사야 합니다. 예산 안에서 맞추고, 결재 올릴 비교 근거도 필요합니다.

> 사용자: 20명 사무실 탕비실 한 달 치. 커피믹스, 종이컵, 화장지, 생수. 예산 20만 원.
>
> 에이전트: 커피믹스는 100개입과 180개입 중 180개입이 개당 ○원 더 쌉니다. 이 기준으로 짜면 B마트에서 총 ○○원으로 예산 안에 들어옵니다. 결재용 비교표를 만들어 드릴까요?

**에이전트가 하는 일**: 인원과 기간으로 필요한 수량을 추정하고, 용량과 단위량으로 단가를 계산해 이득인 규격을 고릅니다. 예산을 넘으면 규격이나 매장을 바꿔 다시 맞춥니다.

**데이터 한계**: 커피믹스, 종이컵 같은 소모품이 상품 목록에 있는지 아직 확인하지 않았습니다. 상품이 소비자용 규격 위주라 업소용 대용량은 없을 수 있습니다.

### 시나리오 3. 가격표를 보고 비싼지 궁금한 소비자

**상황**: 마트에서 식용유 가격을 보고 요즘 오른 건지 궁금한 소비자입니다. 어디서 살지보다 지금 사도 되는지가 궁금합니다.

> 사용자: 백설 식용유 1.8L 요즘 비싸진 거야?
>
> 에이전트: 최근 8주 조사 기준 평균 가격은 ○원이고, 한 달 전보다 ○% 올랐습니다. 지금 할인 중인 매장은 C마트이고 할인은 ○일까지예요.

**에이전트가 하는 일**: 조사일을 바꿔 가며 같은 상품 가격을 여러 번 조회해 추이를 만들고, 할인 기간이 남은 매장을 함께 알려줍니다.

**데이터 한계**: 조사일마다 호출이 필요해 하루 2,000건 한도 안에서 캐싱이 필요합니다.

## 개인정보 처리

서버는 사용자 정보를 저장하지 않고, 대화는 브라우저 탭이 열려 있는 동안만 유지됩니다.

| 항목 | 원칙 |
| --- | --- |
| 대화 저장 | 브라우저 `sessionStorage`만 사용. 탭을 닫으면 사라짐. 서버 DB 저장 없음 |
| LLM 전송 | 선택지로 받은 값은 LLM에 보냄. 이 값들만으로는 신원 특정에 한계가 있음 |
| 서버 로그 | 채팅 내용과 선택값을 남기지 않음 |
| 공공 API 검색어 | 사용자 문장을 그대로 넣지 않고 LLM이 뽑은 키워드만 보냄 |
| API 키 | `.env`에 두고 `.gitignore`로 제외, 저장소 밖에서 팀에 공유 |

참가격 API의 요청 파라미터는 조사일, 업체ID, 상품ID, 코드 분류뿐이라 사용자 정보가 정부 API로 가지 않습니다. 다만 판매점 좌표를 써서 "내 주변 마트" 기능을 넣으면 사용자 위치를 받게 되므로, 그때 위치를 LLM에 보낼지 다시 정합니다.

## 활용 API: 참가격 생필품 가격 정보

[한국소비자원_생필품 가격 정보](https://www.data.go.kr/data/15158701/openapi.do)는 무료·자동승인이고, 개발계정 트래픽은 2,000, 응답은 XML입니다. 공공누리 1유형이라 출처 표시가 필요합니다.

| 오퍼레이션 | 요청 | 주요 응답 |
| --- | --- | --- |
| 기준정보 `getStandardInfoSvc.do` | 코드 분류(`classCode`) 필수 | 단위, 용량, 상품분류, 업태, 지역 코드표 |
| 판매점 `getStoreInfoSvc.do` | 없음 = 전체, `entpId` = 한 곳 | 업체명, 업태·지역 코드, 주소, 전화, X·Y 좌표 |
| 상품 `getProductInfoSvc.do` | 없음 = 전체, `goodId` = 하나 | 상품명, 소분류, 제조사, 용량·단위량과 단위 |
| 가격 `getProductPriceInfoSvc` | 조사일(매주 금요일) 필수 + 업체ID 또는 상품ID | 가격, 할인 여부·기간, 1+1 여부 |

가격은 한 번에 전체를 받을 수 없어, 판매점별 또는 상품별로 나눠 불러야 합니다. 판매점 수에 따라 하루 2,000건 안에서 나눠 받는 계획이 필요합니다.

## 다음 단계: 데이터 분석으로 타깃 정하기

참가격 API를 실제로 호출해 데이터를 분석하고, 어떤 기능을 구현할 수 있는지 테스트한 뒤 타깃을 정합니다.

분석으로 확인할 후보 (이전 대화에서 나온 것, 확정 전):

- 업태별 판매점 수와 창고형 매장 포함 여부
- 화장지, 종이컵, 커피믹스, 생수 같은 소모품이 상품 목록에 있는지
- 할인·1+1 필드가 실제로 얼마나 채워져 있는지

분석 전에 정할 것:

- [ ] 공공데이터포털에서 이 서비스 활용신청, 키를 `.env`에 준비
- [ ] 분석으로 알고 싶은 것 확정
- [ ] 분석 스크립트 언어·도구
- [ ] 코드를 둘 팀 저장소

## 제약과 일정

실질 개발 기간은 4~5주이고, 주차별 계획은 아직 없습니다.

- **LLM**: 무료 API 사용. 팀원끼리 키를 공유하기 편해서. 업체는 미정
- **팀 작업**: 인원과 역할은 미정
- **트래픽**: 참가격 API 개발계정 2,000. 가격을 판매점·상품별로 나눠 불러야 해서 한도 안에서 받는 계획이 필요합니다
- **AI 작업 가드레일**: 키를 다루지 못하게 하는 설정을 GitHub 저장소로 공유 (구체 내용 미정)

## 미정 사항

아래가 정해져야 구현 계획을 세울 수 있습니다.

- [ ] 타깃 사용자와 구체 기능 (데이터 분석 뒤 결정)
- [ ] 핵심 변수: 이 설계에서 결과를 가장 크게 좌우하는 것
- [ ] 위치 기능을 넣을지, 넣는다면 위치를 어떻게 다룰지
- [ ] LLM 업체와 팀 인원·역할
